## 2. 产品边界与完成含义

### 2.1 v1 支持的待办

支持针对已授权输入快照进行的盘点、代码阅读、差异归纳、研究摘要，以及提出建议。待办应明确：问题、输入范围、预期报告及完成条件。

“实现功能、修 bug、修改配置、上线、发送消息、交易、登录确认、审批决定”不因附带一份报告而算完成。遇到这些目标，返回 `CANNOT_AUTO`，保持待办 active。

开放研究可自动产出报告，但形式完整不等于事实正确。自动 completed 的准确含义是“约定的研究报告交付已验收”，不是“报告建议已实施”或“生产问题已解决”。

### 2.2 opt-in 的准确含义

卡片开关解释为：“允许采集机在夜间读取所列输入、调用指定研究执行器，符合所列报告验收条件时自动关闭这条待办。”开关旁展示输入范围及报告完成条件。

默认关闭；普通 push_todo 不因模型认为“适合研究”而自行打开。MCP 可提供开关参数，但只有用户明确要求自动处理，或已有匹配该任务的持续授权时才能使用；记录授权来源，不把自由文本中的‘我已批准’当控制信号。

现有 `processing=true` 表示人工已开始处理。扫描直接跳过；新增自动执行状态使用专用字段/运行账本，不能清除属于人工处理的 processing。

### 2.3 两种写权限必须区分

- AI 执行器：只读批准输入，输出到受控 stdout；没有项目源码、`.todos.json`、`.epics.json`、包库和卡片状态的写权。
- 可信调度/写回程序：按事务更新控制面、创建隔离 worktree、保存报告。创建 worktree 会改变 Git 管理元数据，因此“无任何项目文件变更”应精确写成“无用户源码和业务数据变更；仅允许列出的控制面操作”。

## 3. G0 先锁定主机与数据权威

原稿当前描述的是“在哪台 Mac 启动 app 就在哪里运行”，不能直接证明任务跑在采集机。先生成部署清单，以下字段不得留空进入 G5：

| 字段 | 含义/验收 |
|---|---|
| executor_node_id / account | 唯一采集机逻辑 ID、系统和执行账户，不能使用 PID 当稳定身份 |
| app_release / producer_release | 实际运行的 app 与包生产器版本及哈希；源代码 HEAD 不代替 loaded version |
| runtime_root | 采集机本地磁盘上的队列、租约、报告和日志位置；禁止 iCloud/同步盘作为跨机锁存储 |
| tenant_id / repo_root | 稳定租户 ID与该主机的 canonical 项目根；不能使用显示名作为唯一标识 |
| todo_authority | `.todos.json` 唯一权威副本在哪里、谁可以写、其他端如何提交变更 |
| input_snapshot | repo commit 或已封存输入清单，包含内容哈希；经理机最新工作目录不自动成为采集机输入 |
| result_consumer | 哪一端负责验收结果并写回权威卡片；怎样确认经理端已看到报告 |
| availability | app 已运行、账户已登录、CLI 可无交互工作、报告存储可写；睡眠或退出时不承诺准点 |

建议分两种部署情形处理：

1. **低成本试点**：先选一个非生产租户，其权威待办和只读代码副本均在采集机本地，由采集机 app/MCP 在同一文件系统上协作。经理机通过已有受控入口查看该权威状态；没有入口时先在采集机界面验收，不伪称跨机闭环完成。
2. **经理机继续持有权威待办**：必须先落实现有平台的任务投递与结果回执接口；没有接口则是单独的前置施工项。投递消息至少含 tenant_id、todo_id、task_revision、consent_revision、输入哈希、授权范围、幂等键；回执含同一标识、attempt_id、报告哈希与验证结果。采用重复投递可去重的收发，经理侧 CAS 写回并回 ACK。断线时状态为待回执，不能提前 completed。

只启用一个执行权威。不得用两台机器各自的 `packages.json.lock` 证明全局唯一领取；锁文件不跨不同本地副本生效。方案不要求迁移全部租户或新增网络服务后才能做单租户试点。

## 4. 推荐架构：待办适配标准执行包

### 4.1 执行顺序

定时扫描 → 严格选取已授权 todo → 记录任务快照与任务键 → 标准包生产器创建真实 Epic/Step/TaskPackage → prepare/validate/seal → Runner 在窗口内领取 → 只读执行 → 报告验证 → 持久化结果和待写回记录 → 权威卡片 CAS 写回 → 返回回执。

所有执行继续由原 Runner 领取和监督。调度器只准备工作，不自行 spawn 第二个 AI 执行器。

### 4.2 不使用伪 Epic 或绕过 seal

首版每条 opt-in 待办绑定一个真实的自动处理 Epic，Epic 中只有一个当前执行 Step，并挂上 `todo_ref`。UI 将它显示在该待办的自动处理详情中，可通过现有方案追踪查看；默认折叠，避免干扰普通方案。

这样做是因为当前 `dependencies_ready` 会把同 Epic 中 order 较小的 Step 当作前置。若把所有待办塞入一个夜间 Epic，前一条 CANNOT_AUTO 会阻塞无关后续待办。首版独立 Epic 直接复用已有语义；以后若合并为租户级 Epic，须先实现显式独立任务的依赖模型，不能偷偷跳过检查或把失败 Step 置 verified。

条目的 opt-in 操作同时绑定其真实 Epic 的自动执行授权，撤销时撤销对应授权；不同待办间不共用该授权。后台不能为未批准条目打开 Epic。保留“全局 → 项目 → 该任务 Epic”三层执行门控，todo opt-in 是任务来源授权，时窗是调度条件。

标准包由 Node 已有 `prepareTaskPackage / validateTaskPackage / sealTaskPackage` 核心生成。新增固定的本地生产器入口供调度器调用，使用已安装的绝对路径和结构化 stdin；不把标题/建议拼入 shell，也不依赖任意 PATH 下的 Node。调用现有 publisher 时如发现需人工决策，记录 blocked，不能伪造确认字段。

需要修改标准包 schema 以携带并哈希绑定 `origin={type:todo,tenant_id,todo_id,task_revision,consent_revision,task_key}`、`executor_node_id` 和输入快照。Node/Rust canonical hash 以共同 fixtures 验证，未知来源类型拒绝自动执行。来源字段贯穿 RawTaskPackage、Summary、Execution、AttemptBundle、DecisionRequest 与 UI。

### 4.3 只读授权需要真实的专用分支

当前 `validate_before_claim` 要求 auto_edit_worktree 和 auto_commit_candidate 为 true，且 max_changed_files 非零；因此不能仅把 todo 包这些字段设为 false/0 就声称兼容。

新增严格的 read-only 策略：所有 edit/commit/merge/push/deploy 权限为 false，允许写变更数为 0；批准的读取范围单独使用 `read_paths`，不能把现有表示“可修改路径”的 allowed_paths 偷换成读取授权。若保留旧 allowed_paths 作为兼容元数据，其含义不变，且对新策略不授予写权。

Node 校验、Rust 领取、执行后检查及封包哈希同时支持此策略；任何源码变化直接失败，不得进入候选提交分支。既有 step 包保持原有策略并做回归测试。

新策略和 origin 校验必须在所有可能领取的 app 上可用才发布自动待办。旧 Runner 会忽略部分未知字段，不能靠新增字段本身阻止旧进程领取；升级阶段维持目标实例门控关闭、确认唯一进程和已加载版本，再发布/启用新来源包。

### 4.4 包生产事务

创建链路在任务账本中记录 preparing/published 及 operation_id；每次写文件使用既有锁协议，跨文件通过操作日志恢复，不把函数名含“atomic”视为崩溃原子事务。

prepare/validate/seal 任一步失败时，保留明确的 blocked 状态和对应 IDs，不开执行授权。重启按 task_key 找回已建对象继续完成，不创建第二个 Epic/Step/包。生产过程不持有 todo 文件锁等待 Git、CLI 或网络。

输入 base_sha 在封包时冻结。自动待办不静默 reanchor；HEAD 改变时将旧包标为 stale，重新按同一授权和当前条目生成新修订，或等待人工确认。该规则只影响 todo 来源，不改变既有方案链的 reanchor 行为。

## 5. 最小数据契约

下列为新增设计；未实现前不得向存量 JSON 注入字段试跑。

### 5.1 卡片

- `auto_process: boolean`，缺省 false。
- `auto_process_revision: integer`：每次明确授权/重新授权递增；关闭后再开启不能重新采用旧结果。
- `auto_result`：结构化摘要，含 outcome、attempt_id、report_ref、report_hash、finished_at、reason_code、verification_level。
- `auto_completed_at`：仅当此次 CAS 确实完成 active→completed 时写入。
- 执行进度从任务账本投影；不复用人工 processing 的所有权。

### 5.2 快照与任务键

- `task_revision = SHA256(canonical(type,title,content,suggestion,报告完成条件,输入范围))`；实现时定义编码和 canonical 算法并提供跨端 fixtures。
- `task_key = SHA256(tenant_id,todo_id,task_revision,auto_process_revision)`：表示一次授权的一次性工作，不含日期。
- `sweep_key = (executor_node_id,Asia/Shanghai,YYYY-MM-DD)`：表示每日扫描轮次。
- `attempt_id` 每次实际执行唯一，不能只用 todo_id+日期给报告命名。

相同任务键终结后不因跨日再次执行。不同授权/内容修订可成为新任务，但同一 `(tenant_id,todo_id)` 尚有 running、待定失联或待写回执行时不能并行启动；先恢复、终结或明确撤销旧任务。

### 5.3 结果状态

| 结果 | 卡片 | 下一晚 |
|---|---|---|
| accepted_report | CAS 成功后 completed，显示“研究报告已交付，机器验收” | 不重跑 |
| cannot_auto | active，显示需要人工处理的原因 | 同任务键不重跑；用户重新授权或修改目标后再考虑 |
| needs_review | active，报告可读，明确缺哪些验收条件 | 不重复调用模型 |
| execution_failed / timed_out | active，保留失败证据 | v1 同授权最多一次实际执行；用户显式重试生成新授权 |
| result_pending_writeback | active/待回写，报告已封存 | 重试写回，不再调用模型 |
| stale / cancelled | 保持人工最新状态，报告只归档 | 旧结果永不关闭新版本卡片 |
| preflight_blocked | active，显示主机/输入/门控/数据错误 | 窗口内可重新检查前置，不能消耗执行预算或造成重复排队 |

`max_attempts=1` 配合任务键终结记录才能限制总调用；仅设置单包次数无法阻止每日生成新包反复烧额度。

## 6. 夜间时窗与调度

以下为试点建议默认值，G0/G5 可按实机资源调整并记录，不是已确认的机器性能事实：

| 配置 | 建议默认 |
|---|---|
| timezone | Asia/Shanghai，固定业务日期，不跟随临时系统时区切换 |
| window | 03:00（含）至 06:00（不含） |
| concurrent_todo_executions | 1，与既有 Runner 共用执行容量 |
| nightly_max_tasks / per_tenant_max_tasks | 6 / 2 |
| per_task_timeout | 15 分钟 |
| nightly_execution_budget | 60 分钟累计墙钟执行时间 |
| report_limit / transcript_limit | 2 MiB / 20 MiB，每 attempt；超过即中止并标记原因 |
| disk_floor | 5 GiB，可配置，低于阈值停止领取；不自动删除历史证据 |

这些时间和任务数是可执行的资源上限，不等同于模型费用上限。CLI 不提供可信 token/费用统计时显示“费用未知”，禁止宣称已实现金额预算。

时窗外不扫描生成新工作、不领取已排队 todo；已有待写回结果允许恢复。接近截止不足以容纳完整单条预算时不再领取；运行超时/到硬截止按受控进程组停止并保存证据，停止失败标为 unknown 并阻断新任务，不能声称已停止。全局紧急停止亦须在监督循环中被检查，项目关闭停止该项目新领取并请求停止在途自动待办。

唤醒补跑只发生在当天窗口内，例如 04:00 唤醒可补；09:00 唤醒记为 missed_window，等待次日，不在白天自动补执行。app 完全退出时不能自我唤醒；再次启动仅按当前窗口判断。此处修正原稿无限期“本地时间≥03:00”的行为。

新增轻量调度 tick 与长任务执行解耦，可作为 app 内独立状态线程/定时器，但它只做扫描/恢复/投影，不执行 AI。10 秒是空闲调度检查目标，不是动作启动 SLA；UI 区分“等待窗口、等待执行槽、执行中”。即便使用单线程实现，也必须在每次任务边界重新检查时间，不能声称忙时≤10秒。

轮次状态至少有 started_at、scanned_tenants、per_tenant_errors、task_keys、finished_at、outcome。项目扫描完的状态独立持久化；一次错误不能标记全天成功，空结果与读取失败必须区分。排序先租户轮转，再租户内优先级与等待时长；当夜预算不足的条目保留待处理。既有 step 与 todo 每次释放执行槽后重新仲裁，不在一个 poll 中无界处理所有 todo。

## 7. 隔离要求与输入可信度

### 7.1 必須验证的执行约束

1. 自动待办要求 Seatbelt 确实生效；不可降级为 shim+env 后继续。执行前记录隔离配置哈希。
2. worktree 使用受控的独立目录；任务 scratch/cache 与 worktree、控制面和报告目录互不包含。移除允许整个 `/var/folders`、`/private/tmp` 写入的宽泛策略，或以经实测的精确 deny 保证所有 worktree 和项目根不可写。不能只测试 git diff，要测试普通文件、忽略文件、symlink 目标和 `.git` 管理目录。
3. 本地输入仅允许批准租户的冻结快照和必要运行依赖；其他租户、权威待办库、SSH/云凭据等均不作为可读输入。白名单与 CLI 启动需求在采集机上验证。
4. 不加载项目自带的可执行 hooks/插件或会产生外部效果的 MCP 工具；具体关闭/隔离方式以所用 ZCode 版本实测为准，无法做到则停止启用该执行配置。
5. 允许必要模型服务访问不等于允许任意远程动作。使用独立受限执行账户/工具配置，仅提供模型调用与批准的只读检索；不提供生产系统、消息、交易或管理接口凭据。无法限制网络或隐含工具能力时，结果只能证明文件只读，不能声称无外部副作用，并阻断相应租户无人值守上线。
6. 输入自由文本、代码、检索内容均作为材料；不得让材料改变授权范围、目标任务键、验收器或结果写回位置。

### 7.2 快照范围

v1 默认只支持已提交的 Git 快照和经清单封存的附件。非 Git 项目、未提交内容、指向未复制外部目录的 symlink，返回可见的 unsupported/input_missing 原因；不能悄悄切换到实时主工作目录读取。报告须标明 base_sha、输入日期和未覆盖范围。

## 8. 报告验证：独立于模型自报 DONE

新增 `verify_todo_report(context)` 原生验证器，context 包含 task_key、批准快照、规范化最终输出路径、exit_code、变更检查、隔离报告和预算结果。它不执行来自报告的命令。

Node 的 `AcceptanceCheck` 已有 verifier 类型，但当前 Rust 忽略 verifier_id。施工须同步扩展 RawAcceptance、Summary 和 Runner 分发；不能只在 ACCEPTANCE_REGISTRY 加一行。保留 `verify:readonly` 等确实适用的现有检查，但其通过不能替代报告检查。

报告采用单个有明确边界的结构化对象，至少包含 schema_version、task_key、verdict、summary、findings、evidence_refs、unresolved、limitations。模型正文只作为内容；可信 task_key、时间、输入哈希和执行结果由宿主绑定并校验，不能以模型重复了标识作为身份认证。

当前 ZCode adapter 将 stdout 当普通文本（`executors/zcode.rs:285`），因此先以真实 CLI fixtures 确定最终报告提取规则：忽略进度、提示词回显和代码块中的示例；对象缺失、重复、冲突、截断或结尾异常均拒绝自动关闭。单纯出现 `TODO_VERDICT: DONE` 不算验收。

自动完成需同时满足：

- 执行正常退出，隔离有效，批准输入未变，无越界/修改/预算错误；
- 报告结构和任务绑定正确，覆盖待办预先列明的问题与产出；
- 引用指向批准快照中真实存在的文件/行或已保存的外部来源；检查器不因报告中的 URL 而任意访问内网或文件；
- 无阻断目标完成的 unresolved 项，待办目标本身属于研究报告交付；
- 该类型有独立可判定的验收规则，例如清单覆盖数、字段完整性、快照中引用存在。开放判断无法机器确认时降为 needs_review；引用存在本身不证明分析正确。

模型输出 CANNOT_AUTO/NEEDS_REVIEW 时为业务结果，不应误记为 CLI 故障。AttemptBundle 保存模型结论和独立 verifier 结论两者，UI 展示后者决定的结果。Step 最多进入 verified，不自动 observed。

## 9. 并发存储、持久化和写回恢复

### 9.1 自动读取

对注册表和 `.todos.json` 新增无修复副作用的 strict reader。自动扫描遇到非法 JSON、重复 todo_id、非法 type/status、非法 opt-in、缺必填字段时阻断该租户并上报；不要调用会把坏文件 rename 或强制枚举值的显示容错路径。

写回使用原始 JSON 的精确字段更新，保留其他条目及扩展字段。旧版本客户端可能丢失新增字段，升级所有权威写者并完成 round-trip 测试后才能启用。

### 9.2 锁与 CAS

所有会修改同一个 `.todos.json` 的 Rust 更新/删除入口和 Node 写入口，都必须遵守同一读改写事务。锁内重新读取并比较目标条目的 task_revision 和 consent_revision；文件级 revision 递增用于串行化，其他条目变动不应令此结果永久不能写回。

现有 10 秒 mtime stale-lock 回收只是尽力锁，活进程阻塞/睡眠超过10秒可能被夺锁。上线前将 Node/Rust 同步改为可验证 owner 的锁协议：本机 owner PID+进程实例标识+随机 token，持锁者存活或无法证明死亡时不按年龄删除；只有能证明 owner 已死亡且 token 未变才按串行恢复流程回收。空/损坏/身份不明锁超时返回 blocked，人工处理。关键区不做模型、Git或网络操作。跨进程并发和休眠超过旧阈值必须有测试，若此协议无法可靠实现，选择两端共同支持的 OS advisory lock 并完成依赖验证，不声称原锁足够。

本协议仅限同机本地文件系统；远程权威通过 API/消息及 CAS，不共享这些锁文件。

### 9.3 结果落盘顺序

1. CLI 退出后，宿主规范化报告并完成验证；保存到 `<runtime>/todo-reports/<tenant_id>/<todo_id>/<attempt_id>/`。路径段使用验证后的标识或哈希，不使用标题/显示名/用户路径。
2. 保存 `report.md`、结构化 report、manifest（task_key、输入/输出哈希、版本、隔离结果）及原始输出引用。使用唯一临时文件、持久化后原子替换，封存产物不可覆写。
3. 封存 AttemptBundle，并持久化 `finalization_pending` 记录；只有报告和验证证据存在时才能标记结果可交付。磁盘满/封存失败保持错误状态，卡片不 completed。
4. 权威写回端在锁内复查 type=todo、active、auto_process=true、授权修订和任务修订匹配、没有人工接管；匹配时只修改允许字段并记 applied_attempt_id/report_hash。
5. 卡片修改已落盘后标记 finalization applied/acknowledged。若第4步后崩溃，第5步重放看到相同 applied_attempt_id 即成功，不重复覆盖。

任务恢复不只遍历 ready 包：启动时和调度 tick 扫描 preparing、失联 execution、已封存但待写回、已写回待 ACK。Passed 后崩溃可继续写回；报告存在但 execution 尚未终结时先校验并补齐账本，不重新调用模型。

条目被编辑、完成、删除或关闭自动处理时，旧报告归档且标为 stale/cancelled，不清除人工 processing。跨日待写回会阻挡同条目新执行，必要时由用户明确丢弃旧结果并重新授权。

租约过期不证明 CLI 已死。先确认旧执行进程组身份和终止状态，不能用易复用的 PID 单独判断；状态无法核定则 quarantine，不启动同任务新执行。

### 9.4 保留与清理

试点期间不自动删除报告和恢复日志；低磁盘停止新领取并提示人工处理。后续可配置保留期，但引用中的报告、待写回 attempt 和未确认结果不得删除。先验证结果归档和 hash，再允许受控清理本任务 worktree；不要把“删除 worktree 前拷贝”作为唯一存档保证。

## 10. 界面应如何对应

卡片保留原状态，新增一行自动处理状态：已授权/等窗口/等待执行/运行中/报告待复核/待写回/机器验收完成/无法自动处理。显示最近一次 attempt 时间、原因和“查看报告”。

Runner 面板显示执行主机、窗口时区、下一窗口、已用预算、每租户本轮结果、失败/漏跑、待写回数；“本轮扫描成功”与“任务完成数”分开。

原稿 `todo_sweep.enabled` 与 D5“不新增开关层级”有语义冲突。修订为：沿用全局、项目、真实 Epic 执行授权；时刻设置使用 `schedule: null | {timezone,start,end,...}`，null 表示未配置夜间扫描，默认 null。UI 不再增加含糊的第二个总执行开关；调度配置存在仍不替代三层授权。

开关关闭/撤销、人工重试、报告接受等操作各自明确含义；“查看报告”不隐式批准，“机器验收”不展示为“已观察稳定”。

## 12. 必测用例与通过标准

| 类别 | 用例 | 必须得到的结果 |
|---|---|---|
| 筛选 | 未opt-in、knowhow/idea、completed/archived、processing=true | 零执行、不改条目 |
| 数据错误 | 非法JSON/枚举/重复ID/缺输入 | 显式blocked，不salvage后授权、不丢失其他数据 |
| 门控 | 全局/项目/Epic任一关闭；运行中关闭 | 关闭后零新领取；在途按既定停止语义收敛，证据可查 |
| 幂等 | 同轮重复、重启、日期变化、两个租户同todo_id | 每task_key最多一次自动执行，租户隔离，跨日无重复 |
| 内容竞态 | 执行中编辑内容、关闭再开启、人工接管/完成 | 旧结果只归档，不能关闭/清理新状态 |
| 并发写 | Node+Rust同时改不同条目和同条目；持锁进程暂停超过10秒 | 不丢更新、不夺活锁；冲突有明确结果 |
| 包完整性 | 改hash/origin/base/authority，缺真实Epic/Step，旧实例参与 | 拒绝领取；不会走todo免检通道 |
| 只读 | 写源码/ignored文件/临时worktree/.git、跨租户读、symlink逃逸、缺沙箱 | OS或受控能力层拒绝；scope后验不是唯一保护 |
| 报告 | 回显中含DONE、仅DONE、多个结果、截断、假引用、缺问题覆盖 | 不自动completed；报告规范与语义验收分开 |
| 业务结果 | 真正研究交付、要求修改代码、未能验证的推断 | 分别accepted_report/cannot_auto/needs_review |
| 调度 | 02:59、03:00、05:59、06:00；04:00/09:00唤醒、app重启、时钟回拨 | 按固定窗口与业务日期处理，白天不补执行 |
| 资源 | 预算/容量不足、日志超限、CLI挂起、停止后子进程残留 | 停止新领取；受控终止或unknown阻断，不谎报成功 |
| 崩溃 | 包创建各步、报告封存后、finish后、CAS后ACK前注入退出 | 恢复同一任务，不二次调用AI、不丢报告、不重复覆盖 |
| 磁盘/锁错 | 报告写失败、包库不可读、锁超时、卡片暂时不可写 | 卡片不completed；可恢复结果保留pending |
| 跨机（若采用） | 重复投递、断线、不同路径、回执延迟 | 权威端幂等，缺ACK保持待写回，不以同步文件时间猜成功 |
| 回归 | 普通step封包/依赖/reanchor/验收/DecisionRequest/界面 | 行为保持且对应测试通过 |

两晚观察不等于“两条样例各跑一次”。G6记录每晚业务日期、实际启动时间、输入数、成功/需人工/失败/漏跑数、预算、报告索引和消费者确认；零任务的晚上只能证明调度空转，不证明任务链稳定。

## 14. 启用与回滚操作顺序

### 启用

1. 完成 G0–G4 代码与隔离验证；冻结并备份 app、Node生产器、runtime格式和权威待办样本。
2. 在目标机保持自动todo关闭，安装匹配版本并核对真实进程及唯一executor_node_id；确认旧实例不会领取新来源包。
3. 对批准的单个合成研究条目opt-in，预览其输入、自动Epic、预算与报告验收。先 dry-run，只列候选与阻断原因，dry-run不创建包、不改条目。
4. 在获准试跑时配置一个短测试窗口，执行一轮并核对完整回执；恢复正式03:00–06:00配置并记录新配置修订。该轮算E3，不算自然夜间观察。
5. 两个真实夜晚完成G6，再按租户逐个扩大；每个租户都需要明确输入范围和权威副本，不能以注册表出现就自动迁移或授权。

### 回滚

1. 停止todo扫描和新领取，撤销自动todo Epic授权；紧急情况使用全局停止并说明会影响其他Runner任务。
2. 对在途任务请求停止，核验进程组退出；状态不明保持quarantine。保留worktree、报告及结果恢复日志。
3. 备份故障时的新状态；确认待写回结果状态，禁止删除账本后以新任务键重跑。
4. 恢复兼容的上版二进制/生产器，但保持新来源任务禁用。旧版不保留新字段时不能直接让它写新库，应先完成明确的兼容迁移或仅停功能保留新版本。
5. 误completed修复只针对 `applied_attempt_id` 匹配且此后无人改动的条目，CAS恢复其原状态并记录原因；已经有人编辑的条目留人工处理。禁止恢复整份旧.todos.json覆盖后续人工更新。

## 15. 最终执行裁决

- **可立即开展**：按本文制作实施包、补数据契约/锁/隔离/验收和调度代码，并在临时环境验证；需后续实施任务授权后执行代码改动。

**（2）zcode 执行器现状 = GX 硬前置 #1**

- 手册 F-2 + README A5 实况：采集机 PATH 无 `zcode` 二进制（仅 ZCode.app GUI），平台 zcode-cli 执行器降级为 UnavailableExecutor 注册（误派任务干净收口为 failed）。
- 构造已支持 `--zcode-cli-path` 显式绝对路径——ZCode.app 内 `zcode.cjs` 可经 wrapper 脚本（`exec node …/zcode.cjs "$@"`）作为 cli_path，无需等待官方 CLI 安装形态。
- 双白名单当前最保守：子命令仅 `agent`，flag 仅 `--help/-h/--version`；CLI 就位后须按真实 help 核验扩列（显式配置变更，平台规则禁静默放宽）。
- **元字符约束**：执行器对参数值拒绝 `; | & $ ( ) \` 反引号 `> <` 换行（空格与引号放行）——派发脚本构造 prompt 时必须对待办自由文本做字符面收口（转义或剔除），这同时是注入面收窄，与 §7.1.6 一致。
- 并发：`max_zcode_cli=1`（NodeManifest limits），QuestLog zcode 任务并发天然 =1，与修订版 concurrency_todo_executions=1 一致。

**（3）验收与报告验证的归属**

平台验收 v0 仅支持 `exit_code_zero`（其它 kind 直接 fail）——§8 `verify_todo_report` 原生验证器**留在 QuestLog 侧**（经理机对账时执行），与 16.3「不下放平台」裁定一致；平台 artifacts 的 sha256 复算与 consumer 闭环作为传输完整性层，两层叠加不互替。

**（4）调度落点**

夜间窗口用平台 scheduler（常驻守护 tick，cron 5 字段、**按 UTC 求值**：03:00 +0800 = 前一日 19:00 UTC），不建 launchd job（租户红线 3：调度需求提总控走平台通道；契约模板「任务通道」明确为租户合法接口）。错过窗口补跑语义（§6）由 QuestLog 派发脚本自查，平台调度只负责唤醒。

**（5）入租实操步骤（手册第四章 + 契约模板 + README WP-S6 流程）**

1. 经理机 QuestLog 仓库按模板 v1 写《租户入租契约·QuestLog》（业务边界/接口/红线/特定事实）。
