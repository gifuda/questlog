## 二、四层拆分设计

### 第一性约束：单写者收敛

锁协议实证（file-lock.ts:64-73 ↔ file_lock.rs:84-92）：`.lock` 兄弟文件 + O_EXCL + `kill(pid,0)` 探活——**pid 是本机语义**。跨机双写时互斥失效（死主遭抢锁或永久阻塞，tmp+rename 沦为 last-writer-wins）。因此一切设计服从一条铁律：

> **切流后，板数据与 questlog-runtime 的全部写者进程必须物理运行在 m5p 本机。M4 侧零写者。**

## 三、读面选型裁定（推荐：最小 API；否决 SMB 挂载主路径）

**裁定：M4 读面走 m5p headless 内置 HTTP API（绑 tailnet 接口，tailnet ACL 即边界——sync-server :5888 同模式先例），读写端点分离：读端点全量，写端点最小集（开关/resolve DR/todo 状态推进），写端点在 m5p 本机内走既有 store 锁协议，天然单写者。**

否决 SMB/Tailscale 挂载（含 autofs）作为主路径，理由三重：

1. **fsevents 不跨网络卷**（读面约束已冻结）——无论挂载还是 API，M4 都必须换轮询。两案同罚，挂载无新鲜度优势。
2. **SMB 的失败形态更糟**：m5p 重启/网络抖动 → 挂载点 stale → 进程内 std::fs 读**挂起**（不是报错）→ GUI 冻结。API 不可达是明确报错+新鲜度标注（AgeBadge/MorningBriefing 时效告警先例），可做诚实降级。
3. **锁语义不跨 SMB**（pid/flock 均无效）：任何写者经挂载写即破单写者红线；且遥控面（S5 核心）无论如何需要 API——挂载+API 两腿并做等于更多维护面。SMB 挂载连「应急只读兜底」价值都没有（挂载同样依赖 m5p 可达，而其失败形态更差）。

附带裁定：**过渡镜像桥**（S4 剧本内置，见 §五）是切流→S5 完成之间的 GUI 只读兜底，属临时 rsync 腿而非挂载。

5. **M4 重指**：config.json todo-board → ssh stdio（绝对路径）；hooks.Stop 节点移除（暂停）
6. **NAS 腿**：M4 bootout com.questlog.board-snapshot；TopLEe bundle 腿拆出独立 plist **留 M4**（源仓不动，只写 NAS 不涉板单写者）；m5p 装 board-snapshot plist（先就位 ssh nas 别名 + BatchMode key）。顺序保证 M4 腿先停，避免同日快照目录交叉覆盖

9. **验收单**：
   - m5p 本机会话 list_epics 读到板；M4 会话经 ssh-stdio push_todo → 落 m5p + 桥下轮同步后 M4 GUI 可见

   - headless shadow 跑通 poll（零领取=正常）
   - M4 侧 `pgrep todo-board` 无进程、lsof 板文件零进程
   - 次日 NAS 快照成活（m5p 腿）且 M4 旧腿停
   - collector 恢复后一次真实 dispatch 往返（receipts 落 m5p + finalization 消费）
   - 存量失配包处置单（废止/重封）落档
