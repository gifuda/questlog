# P2-1 镜像桥退役评估（裁决文档）

- 日期：2026-10-15
- 性质：**只读评估**——本文档不改动任何运行中的服务；退役实施需用户批准后另行执行
- 评估对象：`scripts/questlog-bridge-mirror.sh`（launchd `com.questlog.bridge-mirror`，M4，每 20 分钟）
- 结论速览：**可退役，但 marker 必须先迁移为写一次（write-once）所有权**；推荐方案 B，退役窗口建议在 P0/P1 观察期结束后

## 1. 现状链路（实测 2026-10-15 13:40-13:50）

```
com.questlog.bridge-mirror（M4 launchd，20min）
  ├─ rsync m5p → ~/questlog-mirror/（注册表+runtime+板文件，单向只读，12MB）
  └─ 写 ~/.questlog-remote-mode.json（内容恒定 JSON，tmp+mv）
       {"prefix_from":"/Users/power","mirror_root":"~/questlog-mirror","api_base":"http://127.0.0.1:15889"}

marker 消费者（M4 GUI 进程内，data_root::init 启动时一次性读入 OnceLock）：
  ├─ is_remote() → GUI 进入远程模式（读 API/写走远端命令）
  ├─ api_base → remote_client 全部 44+ 远端命令的寻址
  ├─ map_read()/registry_override()/runtime_override() → 本地路径重锚进镜像根
  └─ data_root::guard_write() → 本地写 fail-closed
```

## 2. 谁还在读镜像根（关键问题）

| 调用点 | 执行条件 | marker 存在时的实际状态 |
|---|---|---|
| store.rs read_todos/mutate 等本地分支 | 命令走 local 分支时 | **死路**：44+ 命令全部有 remote 分支先行短路（P0-1 链路分析核实） |
| discovery.rs registry_override/exists() | get_projects 本地分支 | 同上，remote 分支先走 `/api/projects-full` |
| execution_store runtime_override | Runner 执行路径 | M4 无 Runner（headless 遇 marker 拒启，commands 不触发执行） |
| watcher.rs 路径映射 | 远端模式下监听转向 | 远端模式 watcher 跳过本地监听（S5 设计） |

**结论：marker 存在时，镜像根在热路径上零读者。** API 故障时也没有任何代码回退读镜像（remote 分支报错直通 UI，由 S2 离线横条呈现）——镜像不提供离线韧性，纯粹是 S4→S5 过渡期遗产。

## 3. 退役的真正风险点（反例审查）

- **R1 · marker 是模式开关，不是缓存**：marker 缺失 ⇒ `is_remote()=false` ⇒ GUI 回退本地模式 ⇒ 读写直接打 M4 本地板 = **死板分裂脑复活**（P0-2 刚消灭的问题）。因此退役绝不能顺手删 marker；桥的 marker 写职责必须先有新归属。
- **R2 · marker 内容恒定、无新鲜度检查**（grep data_root 无 mtime 逻辑）：写一次即可长期有效，不需要周期性重写。桥每 20 分钟重写同一份 JSON 属于无信息量的操作。
- **R3 · 桥自身故障语义安全**：rsync 第一步失败即 `exit 1`（marker 最后写），m5p 长时间不可达不会破坏 marker。
- **R4 · 并存的其他桥**：`com.gros.board-mirror`、`com.quota-board.bridge` 是另外两套系统的镜像（GROS/额度板），**不在本评估范围**，退役时勿误伤。
- **R5 · 观察期耦合**：P0/P1 修复刚上线（离线横条、异步轮询等尚未经用户日常观察确认）。桥退役后再观察出新问题，会引入"是不是退役引起的"归因噪音。建议退役排在观察期之后。

## 4. marker 写职责迁移方案对比

| 方案 | 做法 | 优点 | 缺点 | 判断 |
|---|---|---|---|---|
| A. 隧道 plist 兼职 | api-tunnel 启动脚本里加写 marker 步骤 | 零新文件；依赖关系自表达（隧道=远程模式前提） | 给承重的隧道 plist 增职责，改动面涉及网络红线敏感文件 | 否决：改隧道 plist 需额外谨慎，收益不成比例 |
| **B. 写一次安装脚本（推荐）** | `deploy/m4/enable-remote-mode.sh`：幂等写 marker（同一 JSON），装机/排障时手动跑一次 | 零常驻进程；marker 语义显式化（"这台机器是远端客户端"是一次性事实，不是周期状态）；回滚=删 marker | 依赖人跑一次脚本（可写入部署手册步骤） | **采纳** |
| C. 桥继续跑 | 现状 | 零改动 | 一台常驻 rsync + 20min 周期负载永续；镜像语义（陈旧只读副本）与 API 客户端模式并存的认知负担 | 否决：过渡件转常驻违背 S4 设计意图（脚本自述"S5 后撤桥删根"） |

## 5. 推荐的退役程序（供实施轮引用；本轮不执行）

前置门（全部满足才动手）：
1. P0/P1 观察期结束（用户确认 ▶ 秒级反馈、离线横条、无周期卡顿）
2. `deploy/m4/enable-remote-mode.sh` 已入库并**已在 M4 实跑一次**（marker 内容与桥写的逐字节一致）
3. 隧道 `com.questlog.api-tunnel` 健康（`curl 127.0.0.1:15889/health` = 200）

步骤（每步有验证与回滚）：
1. 备份：`cp ~/Library/LaunchAgents/com.questlog.bridge-mirror.plist`（时间戳副本）+ marker 副本
2. `launchctl unload` + 移除 bridge-mirror plist（**只动 com.questlog.bridge-mirror，勿碰 R4 两个邻居**）
3. 验证：重启 GUI → 板数据正常加载（API 路径）、无离线横条、写操作（如拖动排序）生效于权威端（m5p 板文件 revision 变化）
4. 观察 24h 后清理：`~/questlog-mirror/`（12MB，纯副本，保留 `.todo-board.json` 一份入备份目录再删）
5. 回滚（任一验证失败）：`launchctl load` 恢复桥 plist；marker 若被误删 → 重跑 enable-remote-mode.sh；镜像根未删前一切照旧
