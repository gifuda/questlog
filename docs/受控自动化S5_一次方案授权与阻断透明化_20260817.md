## 二、修复设计（已吸收 adversarial-auditor 2026-08-17 审查：2 BLOCK + 7 WARN）

### 审查修订
- **B1 采纳（前端消费点穷举）**：防御排序升级为组件级 `useMemo` 生成排序后数组，**全部消费点统一**——L569 步骤渲染、L610 existingSteps（依赖下拉）、L931 actionable 过滤、L411-413 焦点/下一步 find，一律用排序数组。
- **B2 采纳（六层优先级）**：`global_kill_switch > project_disabled > runner_thread_alive（Runner 离线）> epic_auto_execute_off > already_in_flight > acceptance_unregistered`——acceptance ⑨ 明文要求的三类（总闸/项目信任/Runner 离线）全部入列。
- **W1 采纳（诊断纠正）**：MCP `list_epics` 工具层已按 order 排序——真正缺口是 **Rust `epics_to_json`（App 唯一数据源）与 `epic-store.ts` `listEpics` 函数本身**；实施改为这两处 + TS 端次级键对齐 `(order, created_at)`。
- **W2 采纳（测试可达性）**：Rust 测试放 `commands.rs` 内部 `#[cfg(test)]` 直接调私有 `epics_to_json`。
- **W3 注脚**：UI 焦点 = 推荐序（order 最小的 actionable）；Runner 领取序独立（poll 按 order 前置约束判定）——两者各自稳定，不承诺逐次一致。
- **W4 采纳（措辞+口径）**：「稳定序」（Rust 稳定排序 + created_at 次级键）；TS `actionableSteps`/`listEpics` 补次级键对齐。
- **W5/W6 注脚**：already_in_flight 超时升级与 autoExec 状态滞后为已知边界（记录，不在 S5 扩展）。

### 1. order 稳定排序（acceptance ⑩）

- **后端强制层**（Rust）：`epics_to_json` 的 epic_steps 按 `(order 升序, created_at 升序)` 稳定排序——Runner 领取序（MCP shadow_pick/poll 按 order 前置判定）与 UI 序从此同源
- **MCP 防御层**（TS）：`epic-store.ts` 的 board/list 输出 steps 同规则排序（对 MCP 消费方一致）
- **前端防御层**：`EpicBoard.tsx` 渲染前 `[...epic.steps].sort((a,b)=>a.order-b.order)`（后端序被破坏时不失真）；actionable 焦点取排序后首个
- 排序键带 created_at 次级键：order 相同（手工调序）时稳定可预期

### 2. 唯一阻断原因（acceptance ⑨）

`verifyPickupReadiness` 加 `primary_blocker`：按**因果优先级**取第一个——
1. `global_kill_switch`（总闸：急停，一切之上）
2. `project_disabled`（项目信任：一次性设置）
3. `epic_auto_execute_off`（方案授权：正常操作唯一需要动的开关）
4. `already_in_flight`（无需操作，等结果）
5. `acceptance_unregistered`（补注册表）
工具输出首行改为「唯一阻断原因：…（其余次要）」；语义文案随层标注（急停/一次性/每方案一次）。

### 3. App 阻断原因显示

- EpicBoard 的 epic 头部加 auto_execute 状态标记与「为什么没在跑」tooltip：从 `projectStatus.global_enabled` + `project_enabled` + epic.auto_execute 三态推导唯一主因（复用同一优先级文案）
- Settings/useRunner 已有全局状态 ✓ 不动
